# 會議／訪談 → 事實

把一段對話變成後面所有階段都能引用的來源文件。這一階段的價值全在**誠實**：分清楚「對方真的說過的」、「我們推論的」、「完全沒提到的」。事實被污染，後面的 spec 就是憑空想像。

輸出到 `docs/discovery/<YYYY-MM-DD>-<slug>.md`，範本見 `templates/discovery.md`。

## 步驟

1. **先看素材規模。** 逐字稿很長就分段讀完再寫，不要邊讀邊下結論。同一場會議的多個來源（錄音轉文字 + 手寫筆記 + 會後訊息）先合併時間軸。
2. **抽事實。** 每一條都附原句引用（`> 原句` 加時間戳或行號）。引用不到原句的東西不是事實。
3. **抽決定。** 誰決定的、什麼時候、有沒有反對意見。會議上被否決的方案也要記，它會回來。
4. **抽未決問題**，並分成兩類：
   - **只有人能回答**：定價、優先順序、法遵、對外承諾。留給下一階段追問。
   - **可以自己查**：現在系統怎麼做的、有沒有這張表、第三方 API 支不支援。**不要留給使用者，自己去 repo 或文件查，查到就寫進事實區並註明來源檔案。**
5. **抽需求候選。** 用「誰／要做什麼／為了什麼」寫，一條一行，附上它來自哪條事實。這是 spec 的原料，還不是 spec。
6. **抽風險與反訊號。** 對方猶豫的地方、講不出具體例子的地方、避開的問題。這些最容易在會後被自動忘掉，寫下來。
7. **建名詞表。** 對方用的業務詞彙（他們叫「案件」你叫「工單」）。之後 spec、UI 文案、資料表命名都用他們的詞。

## 鐵則

- **不要把推論寫成事實。** 「客戶希望有 dashboard」如果對方只說了「我每天早上要看昨天的量」，那就照原話寫，dashboard 是你的解法，放需求候選。
- **不要補完對方沒說的。** 沒提到權限、沒提到匯出，就在對應段落寫「未提及」。空白比填滿更有用，因為下一階段會針對空白追問。
- **數字要抄原話。** 「大概兩三百件」不要寫成「300 件」。模糊的數字標成待確認。
- **多個人講話要標人。** 同一場會議裡使用者、老闆、工程師的意見權重不同，之後衝突時要知道去問誰。
- **語氣不要打圓場。** 對方說「這個現在很痛」就寫很痛，說「還可以啦」就不要美化成需求。

## 收尾

寫完檔案後回報三件事：抓到幾條事實與需求候選、有幾個未決問題卡在「只有人能回答」、以及你認為這場會議**最重要但最模糊**的一句話是哪句。

接著進 [grill-to-converge](../grill-to-converge/SKILL.md) 把未決清單問到清空；整條流程見 [idea-to-ship](../idea-to-ship/SKILL.md)。
