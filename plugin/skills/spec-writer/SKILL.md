# 寫規格

把決定變成一份**可以拿去驗收**的文件。判準很簡單：另一個工程師只讀這份 spec，不問你任何問題，能不能做出同一個東西並知道自己做完了？

輸出到 `docs/specs/<YYYY-MM-DD>-<slug>.md`，範本見 `templates/spec.md`。

## 前置檢查

開始寫之前確認：

- `docs/discovery/` 有整理過的事實與決定。沒有的話先回 [meeting-to-facts](../meeting-to-facts/SKILL.md)。
- 沒有 blocking 的未決問題。還有的話先回 [grill-to-converge](../grill-to-converge/SKILL.md)，不要用猜的填進 spec。

## 怎麼寫

1. **每條需求標來源。** 寫成 `（來源：F3、D1）` 指回 discovery 的編號。標不出來源的，只有兩種處理：搬進「假設」區並註明要怎麼驗證，或刪掉。**不要靜靜地把自己的想法寫成需求。**
2. **先寫非目標。** 這一輪不做什麼，寫得比目標更具體。這是唯一能擋住範圍膨脹的東西。
3. **驗收條件用 Given/When/Then**，每條都要能被自動測試或被人手動照著點一遍。「效能良好」不是驗收條件，「1000 筆資料下列表在 1 秒內回應」才是。
4. **列畫面清單。** 每個畫面要有名稱、用途、關鍵元素、以及**空／載入／錯誤／權限不足**四個狀態要不要處理。下一階段的介面設計直接吃這張表。
5. **資料模型寫欄位與約束**（型別、必填、唯一、外鍵、刪除行為），不要只畫概念圖。
6. **API 合約寫請求與回應的實際形狀**，含錯誤碼與權限要求。
7. **切版本。** M1 是「能上線給第一個真實使用者用」的最小集合，其餘丟 M2。如果 M1 看起來要做兩週以上，那它不是 M1。
8. **用使用者的詞彙。** 名詞照 discovery 的名詞表，UI 文案與資料表命名之後才不會各說各話。

## 不要寫進 spec 的東西

- 框架選擇、檔案結構、要不要用某個套件——那是 [implementation-plan](../implementation-plan/SKILL.md) 的事。只有當某個技術限制是需求（例如「必須跑在客戶內網」）才寫進來。
- 「未來可能會…」「之後也許支援…」。要麼進 M2 清單，要麼刪掉。
- 沒有驗收方式的形容詞：直覺、好用、快速、彈性。

## 收尾

寫完做一次自我檢查再交出去：

- 每條需求都有來源，或被標為假設。
- 每條需求都有對應的驗收條件。
- 每個畫面都有四種狀態的處理決定。
- 非目標不是空的。
- 未決假設區裡的每一條都寫了「怎麼驗證」。

回報：M1 有幾條需求、幾個畫面、還有幾條假設沒驗證，以及**你認為最可能在實作時被打回來的那條需求**。

接著進 [design-ui](../design-ui/SKILL.md)。整條流程見 [idea-to-ship](../idea-to-ship/SKILL.md)。
