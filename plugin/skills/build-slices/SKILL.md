# 切片實作

照 `docs/plans/` 的切片一片一片做完。這裡的難處不是寫程式，是**維持紀律**：不要一次動太多、不要偷偷擴大範圍、不要把失敗的測試繞過去。

## 每一片的循環

1. **讀計畫裡這一片的定義**：要實作哪些驗收條件、改哪些檔案、怎麼驗收。
2. **讀要改的檔案**（真的讀，不要憑檔名猜）以及最接近的既有實作，照同樣的模式寫。
3. **實作**。只動這一片需要動的東西。
4. **測試**。這一片對應的驗收條件要有測試；純 UI 的部分至少手動照驗收步驟走一遍並回報結果。
5. **跑檢查**：專案的 lint、typecheck、測試全部要過。有 build 的專案在切片邊界跑一次 build。
6. **commit**，訊息說明這一片做了什麼與對應的 US 編號。
7. **更新計畫**：把這一片標成 done；有偏離計畫的地方直接改計畫文字，讓文件保持是真相。
8. **回報一句話**：做完什麼、怎麼驗證、下一片是什麼。然後才開始下一片。

## 什麼時候必須停下來

- **測試紅了而你不知道原因。** 不要註解掉、不要 skip、不要改測試去迎合實作。先弄清楚是實作錯還是測試錯。
- **實作發現 spec 或計畫是錯的。** 停，回報，更新文件，再繼續。默默改行為是這條 pipeline 最常見的失敗。
- **需要新的依賴、憑證或環境變數**，而計畫裡沒寫。
- **要動到計畫外的既有功能。** 特別是共用元件、既有 API 的回應格式、資料庫既有欄位。
- **這一片明顯比計畫預期大很多。** 回去把它切成兩片再做。

## 鐵則

- **不要順手重構。** 看到旁邊的程式碼很醜，記進 `docs/plans/` 的待辦，不要混在這一片裡。混在一起的 diff 沒人 review 得動。
- **不要一次 commit 三片。** 一片一個 commit，出問題才回得去。
- **不要新增沒被計畫要求的功能**，即使只要五行。
- **不要留 TODO 當交付。** 真的做不完就把它變成一片新的切片並寫進計畫。
- **文案與命名照 spec 的名詞表。**

## 收尾

全部切片做完後：

- 跑一次完整檢查（lint、typecheck、測試、build）。
- 對照 spec 的驗收條件逐條確認，列出「已驗證／未驗證」。
- 回報未驗證的部分為什麼還沒驗證（缺環境？缺資料？需要真人？）。
