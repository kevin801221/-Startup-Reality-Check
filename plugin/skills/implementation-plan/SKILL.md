# 前後端實作計畫

把 spec 與設計翻譯成**一條一條可以動手的任務**，而且每條做完都有可以驗收的東西。輸出到 `docs/plans/<YYYY-MM-DD>-<slug>.md`，範本見 `templates/plan.md`。

## 先搞懂這個 codebase 怎麼做事

寫計畫之前先讀，不要憑一般常識假設：

- 資料層：ORM 是什麼、migration 怎麼產生與執行、權限是寫在 DB（RLS）還是應用層。
- API 層：路由慣例、驗證方式、錯誤格式、哪裡處理認證。
- 前端：資料抓取的既有做法（server component？client fetch？）、狀態管理、表單慣例。
- 測試：測試框架、既有測試的顆粒度、哪些東西這個專案習慣測。
- 部署：跑在哪、環境變數怎麼給。

**沿用既有模式**。引入第二套做法的成本永遠比想像高；真的要引入新依賴，在計畫裡寫出理由與替代方案。

## 計畫要包含什麼

1. **資料層**：新增／修改的表與欄位、索引、權限規則、migration 檔名、既有資料怎麼回填。
2. **後端**：每個 API endpoint 的路徑、權限、輸入驗證、錯誤碼、交易邊界、要呼叫的外部服務與失敗處理。
3. **前端**：路由、頁面與元件樹（標出哪些是既有元件、哪些要新增）、資料流、四種 UI 狀態各由誰負責。
4. **垂直切片**：見下節。
5. **測試策略**：哪些邏輯用單元測試、哪些流程用整合測試、要不要 e2e。不要寫「全部都測」，寫清楚**這一輪測什麼、故意不測什麼**。
6. **風險與回滾**：最可能出錯的三件事、每件的偵測方式與回退步驟。

## 切片規則

- **垂直不是水平。** 一片是「資料庫 → API → 畫面」打通的一條窄路，不是「先做完所有 migration」。第一片做完就該能在瀏覽器看到一個真的能用的動作。
- **一片 ≈ 一個 PR。** 大到需要拆成兩次 review 就再切一次。
- **每片要寫清楚三件事**：改哪些檔案、怎麼驗收（跑什麼指令、點哪個畫面看到什麼）、依賴哪一片。
- **第一片優先打通最貴的風險**（外部整合、權限模型、效能瓶頸），不要從最簡單的 CRUD 開始——簡單的部分不會推翻計畫，難的會。
- **每片都含測試**。沒有驗收方式的切片不算切片。

## 鐵則

- **不要在計畫階段寫實作程式碼。** 需要驗證某個技術可行性時，做最小的 spike 並在計畫裡標明「這是 spike，之後要重寫」。
- **計畫要對得上 spec 的編號。** 每片標它實作了哪些 US／驗收條件，最後才能檢查有沒有漏。
- **spec 有洞就回去補 spec**，不要在計畫裡自行決定產品行為。
- **不要規劃你沒讀過的程式碼。** 先讀再寫，不然計畫裡的檔案路徑會全錯。

## 收尾

回報：切了幾片、第一片是什麼、預計會動到哪些既有檔案、以及**最可能推翻這個計畫的技術未知**是什麼。
